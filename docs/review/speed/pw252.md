# PW-252: fusing the run's numpy glue into parallel kernels (lane 114)

Measured on the 48-core machine, only this lane running, `NUMBA_NUM_THREADS=16`, seed 3199, dt 2 Myr, 100 Myr,
default params, cold process with a 4 Myr L5 warm-up for compile (`docs/review/gpu/scripts/run_sim.py LEVEL 100 out.json --warm 4`,
`--plain` for the untimed wall and `/usr/bin/time -v` for peak memory). Ranking script: `docs/review/speed/pw252_rank.py`.
`timers.py` was fixed on the way: the checkpoint writer thread corrupted the shared stack (a 270 s bogus row under
`save_checkpoint`), so wrapped calls off the main thread are now passed through untimed.

Why the line is drawn where it is: **numba's `exp` is not numpy's `exp`** (`pw252_exp_parity.py`: 4.6% of 4M random
arguments differ in the last bit; `cos` and `sqrt` match exactly). Goldens are hashes, so any kernel that replaces a
numpy `np.exp` moves them. I only ported glue that is exact (cos, sqrt, min/max, ordered sums, copies, integer logic) and
left the exp users for an owner decision (draft-glue-exp-ports-need-ulp-decision).

## 2. What was ported (all bit-identical to the numpy they replace)

| Function | New | Kind |
|---|---|---|
| `noise.fbm` (all octaves of `Perlin3D`) | `noise._fbm`, prange over points | arithmetic in the numpy order (the 3-term dot product is `(a+b)+c`, found by bit comparison) |
| `Simulation._world_view` | `plate_kernels.gather` via `world_view` | 8 fancy-index copies into one prange pass each |
| `Simulation._scatter` | `plate_kernels.scatter` via `write_back` | serial on purpose: several world cells can sample one plate cell and numpy's last-write-wins must be kept |
| `climate.month_temps`, `month_rain`, `_pet` | `_month_temps`, `_month_rain`, `_pet_k` | per-cell passes; sums add months in order like numpy's axis-0 sums; `np.maximum(-0.0, 0)` is `+0.0` (not python `max`), matched |
| `climate.months` snow pack | `_snowpack` | the 2 x 12 month python loop of full-grid ops became one pass per cell |
| `vegetation.summary` | `_summary_a`, `_summary_height` | per-cell loops over the types, no (NP, n) temporaries; the one `np.exp` is taken in numpy on the (n,) vector |
| `vegetation.equilibrium` prologue and `strip` | `_equilibrium_prep`, `_strip` | ~25 (NP, n) temporaries -> one pass |
| `earth.margin_band`, `sheet_surface` edge | `kernels.grow`, `kernels.has_unset_nbr` | `reduceat` over an (edges,) temporary -> neighbour scan |

Each has a fallback to the numpy form for inputs that are not float64/contiguous. Checked with random full-size inputs
(164k cells) bit for bit (int64 view compare, so signed zeros count): temps, rain, snow, water, pet, all `summary`
fields, all `equilibrium` outputs (with and without `nu0`, `migrate`, `substeps`, `snaps`), `fbm` (3 octave/frequency sets),
margin_band/edge on random masks. Speed of the pieces at 164k cells: `month_temps` 19.5 ms -> 1.3 ms, `month_rain` 8.3 -> 0.5 ms,
`summary` 63 -> 5 ms (12x).

Python-side (numpy + interpreter) exclusive total at L7: 146.1 s -> 108.5 s; compiled kernels 128.0 -> 132.7 s (the new
kernels cost 4.0 s in all). Biggest drops at L7: `month_temps` 9.9 -> 0.03 (kernel 0.7), `summary` 6.3 -> 0.2 (0.4),
`_world_view` 5.0 -> 0.2 (gather 0.9), `fbm` 4.5 -> 0 (0.1), `equilibrium` 5.5 -> 0.9 (0.7), `months` 6.0 -> 3.3.

The ticket guessed ~1.3x from fusing half the glue at 4-6x. Measured: **1.13x at L7, 1.11x at L6**, because the glue that
is bit-exactly portable was about 40 of the 146 s; the rest is exp users, sequential flood/route code or ordered scatter-adds.

Goldens: `tests/test_golden.py` (and `test_invariants.py`) pass **unchanged**; no golden was regenerated.

## 4. What a GPU could still take (measured, `climate_step`, `_relax_along`, `_smooth`, `_rain`, `_coarse_down`)

With the glue fused, the share of a step spent in the data-parallel stencil/mass-balance kernels that
`docs/review/gpu/profile.md` marks as GPU candidates (sum of those five kernels' inclusive time, same timed runs):

| Run | Wall | GPU-candidate kernels | Share |
|---|---|---|---|
| L6, 100 Myr | 67.0 s | 22.2 s | 33% |
| L7, 100 Myr | 241.2 s | 79.9 s | 33% |
| L8, **12 Myr only** (cold start; 1062 s, peak 15.6 GB) | 1062 s | 642 s | 60% |

Per call at L7 -> L8: `_rain` 261 ms -> 8.65 s (33x for 4x the cells), `_relax_along` 15.7 -> 359 ms (23x), `_smooth` 2.6 -> 25.7 ms (10x),
`climate_step` 3.4 -> 13.9 ms (4x). The kernels that grow faster than the cell count are exactly the GPU candidates, so
their share rises with level. Sequential kernels (`_stommel` 3.5% at L7, 6.3% at L8; lakes/flood/route) and the remaining
numpy glue (45% of the L7 step, 25% at L8) stay on the CPU.

Reading: at L6/L7 even an infinitely fast GPU can take at most a third of the step (bound 1.5x, before copies and launch
overhead), so it does not pay there. At L8 the candidates are 60% of the step (bound 2.5x). I measured no L9/L10 step
(an L8 100 Myr run is ~2.5 h; L9 is days), so the L9/L10 share is an extrapolation of the above trend and I give no number:
the measured per-call growth says the share goes up, not down. The earlier GPU prototypes (profile.md section 5) measured
`_rain` 16x faster on the GPU than the 16-thread CPU at L8 (copies included), which would turn its 190 s here into ~12 s; that is
the largest single item.
Caveat: the L8 window is 12 Myr from a cold start and may overweight climate updates (3 of them), so treat 60% as an upper-ish
estimate until a longer L8 run is profiled.
